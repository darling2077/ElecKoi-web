# 凭据与主密钥：为什么它不能变，以及变了以后会怎样

## 一句话

`ELECKOI_MASTER_KEY` 是**唯一**能解开用户已保存的 API Key 的东西。
它一旦变化，那些 API Key 就**永久解不开**（AES-GCM，没有后门、没有恢复途径）。
所以它必须固定、必须备份。

## 数据是怎么保护的

| 环节 | 做法 |
| --- | --- |
| 主密钥来源 | 只来自环境变量 / Docker secret，绝不入镜像、不入库 |
| 每租户密钥 | `HKDF-SHA256(masterKey, salt=tenantId)`，跨租户无法互读（断言 K-8） |
| 加密 | AES-256-GCM，密文格式 `web-aes-v1:<版本>:<iv>:<tag>:<密文>` |
| 前缀 | 与桌面端的 `desktop-safe-v1:` 刻意不同，两端数据互不误读 |
| 落库形态 | 库里只有密文，且不含明文片段（断言 K-2） |

## 换过密钥会怎样（2026-09-12 实际发生过）

上游 `ModelRepository` 是**逐行**解密的：

```ts
// 第 18 行，列表
.map((row) => ({ …, api_key: this.cipher.decrypt(row.apiKey), … }))
// 第 30 行，保存时会拿旧密文比对
const apiKey = secret === undefined ? previous?.apiKey ?? ''
  : previous && this.cipher.decrypt(previous.apiKey) === secret ? previous.apiKey : this.cipher.encrypt(secret)
```

于是主密钥一变，两个症状同时出现，用户被彻底锁在外面：

1. **所有 API 供应商凭空消失**——一条解不开 → 整个 `query.models.list` 抛错；
2. **重新添加也失败**——保存时会先解开旧密文，同样抛错，新值根本写不进去。

### 我们的处理：把爆炸半径压到"一个字段"

`WebCredentialCipher.decrypt` **不再抛错，而是告警并返回空串**
（`src/web/platform/WebCredentialCipher.ts`）。效果：

- 供应商列表照常显示，坏掉的那条 `api_key` 是空的；
- 用户在该条目里重新粘贴 Key 保存即可恢复，**其余字段（baseUrl、模型列表、请求头）原样保留**；
- 日志里留下痕迹：`[web] 凭据解密失败（主密钥可能已更换，租户 …）：已按空值处理，请重新填写 API Key。`

注意这一步**不是"吞掉错误"**：主密钥换过之后那条数据本来就救不回来，
抛错只是把"可修复的一个字段"升级成"整个功能不可用"。

## 排查用：主密钥自检

`scripts/` 之外还有一个一次性诊断脚本（本次事故中用来确认影响面），
它对某个租户库里所有 `web-aes-v1:` 密文逐个试解：

```bash
docker run --rm --user 0:0 --env-file docker/.env \
  --entrypoint node -v /tmp/keycheck.js:/tmp/keycheck.js:ro \
  -v docker_eleckoi-data:/data eleckoi-web:dev \
  /tmp/keycheck.js /data/tenants/<租户id>/db/eleckoi-common.sqlite3 <租户id>
```

输出形如：

```
  ❌ model_configs.apiKey rowid=2 len=121
密文字段 1 个，其中解不开 1 个
```

本次事故的结论就是这一行：**只有 `model_configs.apiKey` 一个字段解不开**，
角色、会话、预设、设定库等全部完好——所以问题只值"重填一个 Key"。

## 防复发

1. **compose 强制要求该变量**（`${ELECKOI_MASTER_KEY:?…}`），缺失直接启动失败，
   不会退化成"临时密钥"静默运行（`ELECKOI_ALLOW_EPHEMERAL_KEY` 在本部署里没有开启）。
2. **主密钥另存一份**：`/root/eleckoi-backups/master-key.env`（权限 600，仓库之外）。
   建议再抄一份进密码管理器——它是唯一无法重建的东西。
3. **不要**用 `openssl rand` 重新生成它来"重置"服务；要重置的是某条记录的 Key，不是主密钥。

## 回归测试

`pnpm webui:keys`（8 条断言，已并入 `pnpm webui:verify`）：

| 断言 | 覆盖 |
| --- | --- |
| K-1 / K-2 | 加解密往返正确；库里只有密文、无明文 |
| K-3 / K-4 | 换密钥、桌面端格式、字段残缺、版本不支持 → 一律返回空串 + 告警，**不抛错** |
| K-5 | 库里有坏密文时，列表仍返回全部条目（坏的那条 key 为空） |
| K-6 | 在坏密文之上重新保存成功（用户可自助恢复） |
| K-7 | 未改密钥时旧密钥原样保留（不会被误抹） |
| K-8 | 同主密钥、不同租户解不开（租户隔离） |
