# 上游升级流程（保持"一条线更新"）

## 一条命令的判断标准

升级后跑 `pnpm check:upstream-diff`，**通过**意味着：对上游源码只有新增文件与 `patches/` 里那几个受控补丁，
`git rebase upstream/main` 预期零冲突。这是"后续更新也能一条线直接更新"这句承诺的唯一凭据。

## 标准步骤

> 前置：工作树必须干净（`git status` 无未提交改动）。**发布之后**（本仓库有了自己的提交，
> 见 `docs/webui/GitHub-发布方案.md`）走 rebase 版本；发布之前（零自有提交）才可用 fast-forward。

```bash
# 1. 撤销我们的补丁（不撤的话 rebase 会在这几行上冲突）
node scripts/apply-patches.mjs --revert

# 2. 拉取上游
git fetch upstream --tags

# 3. 把我们的提交挪到上游最新之上
git rebase upstream/main
#    发布前（零自有提交）这一句等价于 git merge --ff-only upstream/main；
#    有自有提交后 --ff-only 必然报 "fatal: Not possible to fast-forward"。

# 4. 重打补丁
node scripts/apply-patches.mjs

# 5. 重建 workspace 包（上游若改了 packages/，类型会指向旧 dist）
pnpm build:workspace-runtime

# 6. 重建渲染产物 ← 最容易漏的一步，见下
pnpm exec electron-vite build

# 7. 全量验收
pnpm webui:verify
```

### 发布前后 `package.json` 的处理不同

- **发布前**（`package.json` 是我们的未提交改动）：先 `git stash push -- package.json`，
  rebase 后再 `git stash pop`。
- **发布后**（`package.json` 已随提交入库）：不需要 stash。上游改 `version` 字段**不会**冲突；
  上游同时也在 `scripts` 末尾追加时**会**冲突，**保留双方即可**（良性冲突）。

## ⚠️ 最容易踩的坑：忘记重建渲染产物

`pnpm webui:verify` 里的浏览器类检查，测的是 **`out/renderer/` 里的构建产物**，不是 `src/`。
升级上游后若不跑 `pnpm exec electron-vite build`，测的就是**上一个版本的前端**——
结论会完全错误。这个坑真实发生过一次：

> 升级到 v0.1.1 后没重建，于是"上游对代码块的修复看起来没生效"，
> 白白排查了很久，实际是浏览器里跑的还是旧 bundle。

现在 `pnpm webui:render` 的第一条断言 **R-0** 专门防这个：
构建产物的 mtime 早于渲染层源码就直接 FAIL，并提示该跑什么命令。

> 注：`docker/Dockerfile` 里每次构建都会重新跑 `electron-vite build`，
> 所以**线上镜像不会踩这个坑**——踩坑的只有本地验证。

## 案例：上游「改名不迁移」——发现、应急、以及上游修复（2026-09-16）

**症状**：预设页面报「预设缺少工具配置。」，所有从 ≤v0.1.1 升级上来的库都中招。

**根因**：上游 `d5d02ec`（v0.1.2）把预设内容键 `tool_policy` 改名为
`tool_configuration`（`CONTENT_TOOL_POLICY` → `CONTENT_TOOL_CONFIGURATION`），
**没有提供数据迁移**。而 `ensureInitialized()` 只在「没有激活预设」时才补种，
老库预设行还在 → 不补种 → 内容表仍是旧键 → 读新键得 `undefined` → 抛错。

**两条通用判据**（下次遇到同类问题直接套）：

- **全新安装测不出来**：新库走 `defaultContents()` 写新键。上游自己的
  `tests/agent-presets.test.ts` 用的就是全新库，8/8 全绿也发现不了。
  **必须拿一份真实老库跑一遍读接口。**
- **桌面端「重装也没用」**：库在 `app.getPath('userData')`
  （Windows `%APPDATA%/ElecKoi/eleckoi-common.sqlite3`），卸载不删数据。

**我们的应急**：写了 `docker/migrate-preset-tool-policy.mjs` + 容器入口脚本自动执行。

**上游的修复**（`8f61b29`，同一个 `v0.1.2` tag 被**强制移动**到新提交）：
把归一化做进了 v1→v2 升级迁移本身（`applyCurrentStorageCleanup` 调用
`normalizeAgentPresetStorage`），另在 `normalizePreReleaseV2` 里覆盖「已经是 v2
但残留旧键」的库。除了改键名，还补齐缺失的工具配置、清理四张表里的废弃
roleplay-plan 行——**比我们的应急方案彻底得多**。

**因此我们的工具已删除**，遵循「上游自带同类修复时删掉我们的实现，不重复维护」。
删除前用真实老库验证过上游修复一次 open 即可生效：

```
打开前          : policy:1, config:0, version:1, baseline:eleckoi-common-v1-2026-09-11-agent-presets
第一次 open 之后: policy:0, config:1, version:2, baseline:eleckoi-common
```

> ⚠️ 这里有个值得记的教训：我最初**从代码推断**上游修复要「启动两次」才生效
> （`normalizePreReleaseV2` 在 version=1 时会提前 return），并差点据此决定保留
> 自己的工具。实测发现推断是错的——归一化在迁移函数内部也调用了一次。
> **升级路径的行为必须拿真实老库实测，不能只读代码推断。**

## ⚠️ 门禁的盲区：它只看工作树

`scripts/check-upstream-diff.mjs` 用 `git diff --name-status <baseline>` 比对的是
**工作树 vs 上游基线**，因此：

**带着已施加的补丁直接提交，门禁照样判通过**——但提交内容里已经写进了被修改的上游文件，
上游一旦改同一处，rebase 必然冲突（已实测复现）。

所以提交前必须撤销补丁，并加一道人工断言：

```bash
node scripts/apply-patches.mjs --revert
git diff --name-only upstream/main       # 只允许 package.json（及已决定修改的 README.md）
# …提交…
git diff --name-only upstream/main HEAD -- src/main src/renderer   # 必须为空
node scripts/apply-patches.mjs           # 提交后再施加回来（构建需要）
```

注意 `src/main`、`src/renderer` 这两条路径的断言和门禁白名单**必须同步演进**：
一旦决定修改 `README.md`（见 `docs/webui/GitHub-发布方案.md` 决策 4），
就要把 `README.md` 加进 `ALLOWED_MODIFICATIONS`，否则门禁会直接判"修改了上游文件"（已实测）。

## v0.1.2 → v0.1.4 实录（2026-09-17）

上游一次性发了 v0.1.3 与 v0.1.4（`main` 直接在 v0.1.4）。**跟到最新那个**，别只跟用户提到的那版。

### 标准动作（按顺序，别跳）

```bash

git log --oneline <我们的基线>..<上游最新>        # 看规模与提交信息

```

### 迁移必须拿**真实旧库**验，不能只看新库能不能装

做法（这一轮用的，可复用）：

1. 把**线上真实**租户目录整份快照到 /tmp（`cp -a`，连 `-wal`/`-shm` 一起）。
2. 记下升级前：`PRAGMA user_version`、各表行数、关键表指纹、表清单。
3. 用**新代码**挂载这份快照（例如 `pnpm webui:import-cards` 指向空目录做一次 dry-run，
   挂载本身就会跑迁移）。
4. 升级后逐项核对：
   - `user_version` 是否到 3、`desktop_schema.baseline` 是否仍是 `eleckoi-common`；
   - **表清单前后一致**（一张不丢）；
   - 关键表行数一致，并对 `characters` / `chat_sessions` / `character_regex_rules`
     做**逐行指纹比对**（比"行数相同"强得多）；
   - `PRAGMA foreign_key_check` 与 `PRAGMA integrity_check`；
   - 迁移**实际改动的行**逐条看过（这一轮 76 条设定 + 1 条预设的
     `position: after_instructions → insert_point_1`，与上游映射表一致）。
5. 线上正式升级**前先备份**（`tar` 整个数据目录），升级后再复查同样几项。

### 基线白名单怎么看

迁移带 `acceptedBaselines`：只有当库的 baseline **不是** `eleckoi-common` 时才校验它。
我们部署的库 baseline 就是 `eleckoi-common`，所以这一关直接跳过 —— 但**别默认如此**，
升级前一定先查清楚自己库里的 `desktop_schema.baseline`，否则可能在启动时被
"无法识别数据库 vN 的结构标识，拒绝修改数据"直接拒绝启动。

### 依赖变化会拖慢首次构建

这一轮上游动了 `package.json` / `pnpm-lock.yaml`，pnpm 安装层缓存失效，
`docker compose build` 要重新下载 900+ 个包——**20–40 分钟属正常，不要中断**。

## v0.1.4 → v0.1.5 实录（2026-09-18）：**上游强推改写了历史**

这一轮遇到的不是普通升级，值得单独记下来——上游把 `main` **强推改写**了：

- 旧的 `v0.1.4`（`46127d4`）成了**孤儿提交**，新的 `v0.1.4` 是 `7f1d0b5`（内容比旧版还多 12 个文件）；
- `git fetch` 会显示 `+ 46127d4...49abc93 main -> upstream/main (forced update)`，
  并且 `v0.1.4` 这个 tag 会被拒绝更新（`would clobber existing tag`）——**这是信号，不是错误**。

### 踩到的坑：普通 `git rebase` 会把上游自己的提交当成"我们的"重放

我们的基线 `46127d4` 不再是新 `v0.1.5` 的祖先，于是 `git rebase v0.1.5` 认为
"从共同祖先到 HEAD 的所有提交都是我们的"，**连上游那个旧的发布提交一起重放**，
结果撞在上游自己的文件上（`.github/workflows/*.yml`、`package.json` 冲突）。

正确做法是 `--onto`，显式指定"只重放基线之后的提交"：

```bash
git rebase --onto v0.1.5 <旧基线>      # 例：git rebase --onto v0.1.5 46127d4
```

判断要不要用 `--onto` 的一句话：**`git merge-base --is-ancestor <旧基线> <新上游>` 为假就必须用。**

### 门禁也跟着误报了（已修）

`check-upstream-diff.mjs` 原来写死优先用 `upstream/main` 当基线。上游强推后
`upstream/main` 可能比我们基于的发布 tag 更新（这次多 3 个提交），于是它把上游那些
更新的文件误判成"我们删了/我们加了"，直接不通过。

已改成：**只有当 `upstream/main` 是 HEAD 的祖先时才用它**，否则在 `v*` tag 里挑
最新的祖先（通常就是我们 rebase 到的那条 tag），并打印实际使用的基线。
仍可用 `ELECKOI_UPSTREAM_REF` 或命令行参数强制指定。

### 依赖大改：必须重装

这一轮上游把 DSH 运行时从 `0.1.1-rc.2` 升到 **`0.1.5-rc.2`**，`package.json` 改 337 行、
锁文件改一万五千行，`patches/` 里的 pnpm 包补丁也跟着改名
（`@deepseek-ai__dsh-llm@0.1.1-rc.2.patch` → `@deepseek-ai__dsh-llm@0.1.5-rc.2.patch`）。

**不重装依赖就会看到莫名其妙的类型错误**，而且错在**上游文件**里
（这次是 `DshAgentRuntime.ts` 报 `provider` 不在 `DshModelIdentity` 里——本地还是旧版 DSH 的类型）。
所以 rebase 之后先 `pnpm install --frozen-lockfile`，再谈类型检查与验收。

### 数据库这一轮不用动

`installSchema.ts` 没改、`CURRENT_SCHEMA_VERSION` 仍是 3，所以线上的 v3 库**不需要迁移**。
但仍然按老规矩用真实库副本挂载一遍确认（挂载即校验），别只看"文件没改"。

### 更新后的标准动作（把这条加进上面的清单）

```bash
git fetch upstream --tags
git merge-base --is-ancestor <旧基线> <新上游> || echo "历史被改写：必须用 --onto"
git rebase --onto <新上游> <旧基线>
pnpm install --frozen-lockfile        # 依赖可能大改，必须先重装
node scripts/apply-patches.mjs && pnpm check:upstream-diff
pnpm webui:verify
```

## v0.1.5 → v0.1.6 实录（2026-09-18）：正常快进的一次

对比上一轮的"改写历史"，这次是标准形态，正好当作流程模板：

```bash

git merge-base --is-ancestor v0.1.5 v0.1.6   # 真 → 普通 rebase 即可

```

## v0.1.7 → v0.1.8 实录（2026-09-20）：多了一个"本地运行时包"要重建

### 2）运行时的冷启动超时会把 Agent 验收打挂（已加重试）

第一次跑全量验收时，Agent 组 9 项挂了 4 项，日志里是：

```
RequestTimeoutError: initialize timed out after 10000ms waiting for dsh profile "sdk"
→ RUNTIME_UNAVAILABLE
```

原因是 DSH SDK 客户端对**运行时子进程 profile 初始化**有 10 秒硬超时

（识别 `timed out` / `RUNTIME_UNAVAILABLE`，重试前清空事件缓冲；第二次仍失败就照常判失败）。
这样既不被环境抖动误伤，也不会掩盖真实回归。

> 同样值得留意：慢机器上真实部署也可能撞到这个 10 秒上限——如果用户反馈
> "第一次发消息失败、重发就好"，先怀疑这里。

## v0.1.8 → v0.1.10 实录（2026-09-27）：上游给插件加依赖，整块插件会静默消失

上游一次发了 v0.1.9 与 v0.1.10（跟最新那条规则再次生效：用户只提到一个版本，实际要跟到最新）。
这次最有价值的教训不是版本本身：

### 1）插件 `inject` 里多一个服务 ⇒ 整块插件不加载 ⇒ 它的路由集体消失

v0.1.10 给 `characterTransferPlugin` 的 `inject` 加了 `'directoryPicker'`（原生目录对话框，
批量导出用）。cordis 的语义是：**inject 的服务缺一个，整个 `apply` 都不执行**——
于是角色卡导入/导出那 5 条路由全部消失，而我们自己的卡片图片搬运正挂在导入那条路由上。

抓住它的是验收里的 **P1-4「网关注册了全部请求路由」**：它不写死数量，而是从
`src/shared/contracts` 里取全部 `requestContracts` 逐个比对，缺一条就报出来。
这条断言当初就是为了"上游新增 Electron 专属路由时立刻报警"写的，这次真的救了场——
否则表现会是"导入卡片突然不能用了"，而排查方向很可能跑偏。

修法不是改上游，而是在**平台层补服务**：`src/web/platform/webDirectoryPicker.ts` 给出 Web 等价物
（导出落到租户 `exports` 目录），并在 `server.ts` 加 `/exports` 列表与下载路由，
把这条链路验到终点（`webui:media` 的 M-5/M-6：目录选择器可用、导出文件能下载、目录穿越被拒）。

> **通用教训**：上游给插件加 `inject` 依赖时，不会报错、不会构建失败，只会静默少一块功能。
> 所以「路由注册完整性」这类**覆盖率型断言**必须常备，且期望值要从契约推导、不能写死数字。

### 2）上游修好了我们的补丁 ⇒ 删掉补丁（第一次实际执行）

补丁 0001 修的是 `LocalMediaStore` 把媒体根路径分隔符写死成 `\`、在 POSIX 上媒体全 404。
v0.1.10 上游自己用 `sep` 替换了硬编码反斜杠，**修的是同一个 bug**。
于是删除该补丁、`patches/README.md` 记一笔——这正是可更新性设计想要的结果：
补丁越少，rebase 越稳。回归仍由 `webui:media` 守着（它验行为，不验补丁存在与否）。

### 3）检查清单又加一条（第六查）

前五查之外，本轮新增：

6. `git diff --stat <旧> <新> -- src/main/modules/` —— 看有没有模块改了 `inject`。
   有则**逐个确认平台层是否提供该服务**，缺失会让整块功能静默消失（见上）。

### 4）界面变化会让"探针"过期，但不该削弱断言

v0.1.10 把生成统计改成「药丸 + 点开看详情」，移动端探针原来找的
`.generation-stats-item` 类名不存在了 → M-stats 报 0 项。修法是**跟着新结构验同样的性质**
（药丸完整显示、不被壁纸吞掉），并顺势把新功能也验到终点（点开后详情面板必须有行），
而不是把断言放宽到"能过就行"。

## v0.1.10 → v0.2.0 实录（2026-09-29）：上游把界面搬进了 DSH 客户端插件体系

这是本 fork 遇到过的**最大一次架构换代**。形态上是普通 rebase（上游没有强推改写历史），
但界面集成方式整个换了，`out/renderer` 那套旧 React 应用在 v0.2.0 已经是死代码。

### 上游改了什么

- 主窗口加载 `${DSH_CLIENT_ORIGIN}/`，即 **DSH 官方 Web 前端**（npm 包
  `@deepseek-ai/dsh-web-frontend` 的 `dist`），由 Electron 的自定义协议 `dsh-app` 同时负责：
  伺服该 SPA、伺服 ElecKoi 的 DSH 页面资源（`out/renderer-dsh`，由上游新增的
  `vite.dsh.config.mjs` 构建）、其余请求反代到 **DSH 插件宿主**。
- 宿主通过 IPC 把 `injections`（`{kind:'global'|'script'|'script-src'|'script-preload'|'style'}`
  、形如 `__DSH_BOOT__` / `__ModuleLoader__` 的门面）交给客户端，客户端自己消费。
- ElecKoi 的界面被拆成一批 DSH 客户端插件（`packages/dsh-client-*`），
  在 **apply 阶段**就使用桌面端 preload 提供的 **`window.eleckoi`**。

### 我们要做的适配（全部在自有代码里，上游文件零改动）

1. **宿主层**：`src/web/http/dshClient.ts`——伺服 DSH 前端并注入 injections 与
   `__ELECKOI_CLIENT_ASSETS__`、伺服 `/eleckoi/assets/*`（来自 `out/renderer-dsh`）、
   其余反代到 `ctx.pluginHost.start()` 返回的宿主地址（带上换 cookie 得来的宿主 cookie）。
   接线路由在 `server.ts`：**我们的 `/api`、`/exports`、媒体、卡片帧优先**，再交给宿主。
2. **桥脚本必须注入 DSH 文档**（`decorateDshDocument` 的 head 最前）：
   `window.eleckoi` 缺席时六个 @eleckoi 插件 apply 全失败，shell 插件因 inject 依赖它们
   而永久 pending，整块界面起不来（表现为 "Failed to load plugin" 列表）。
   这就是 README 里"保留我们的桥脚本"的含义。
3. **WebSocket 反代**：DSH 客户端的传输走 `ws://<本源的源>/api/remote.mux`，
   必须处理 `upgrade` 事件并透传到宿主（`proxyDshUpgrade`），否则一直刷
   `[connection] connection lost`、插件加载失败。
4. **反代要真流式**：`/plugins/events` 是 SSE，`await response.arrayBuffer()` 会把它整体缓冲
   （客户端收不到事件、还会二次写头报 `ERR_HTTP_HEADERS_SENT`）。
5. **改写 `dsh-app://app` 前缀**：插件页面源码里写死
   `import('dsh-app://app/eleckoi/assets/eleckoi-page-*.js')`，浏览器解析不了这个 scheme，
   伺服前端与反代文本响应时统一改写成同源路径（二进制仍流式）。
6. **CSP：nonce + `'unsafe-eval'`**。宿主的 injections 是**内联脚本**，`script-src 'self'`
   会把它们全挡掉（症状是门面/资源表缺失）；DSH 的模块系统还要用 `eval` 装配 classic 插件包。
   因此文档响应按请求生成 nonce（`securityHeaders('app', cardOrigin, nonce)` +
   `decorateDshDocument(..., nonce)`），并放行 `'unsafe-eval'`；脚本来源仍限 `'self'` + nonce。
   **改 CSP 之后必须重跑全部浏览器组**——只跑被改到的那一组会漏掉别的组。
7. **服务与插件顺序**：`agentFileDraftsPlugin` 必须在 `agentPlugin` 之前挂载（提供 `fileDrafts`），
   否则整块 Agent 插件不加载、18 条 `command.agent.*` / `query.agent.*` 路由静默消失；
   平台层还要提供 `fileOpener`（Web 等价物：明确提示去下载页）。
8. **ESM 产物补 `require`**：上游 `DshAgentRuntime` 里有一句 CJS 的 `require.resolve('pnpm')`
   （插件中心用它定位 pnpm），我们构建的是 ESM，需在 `vite.shared.ts` 里注入 `createRequire`。
9. **依赖自检冲突**：上游把 `pnpm@11.7.0` 装成了依赖，脚本里嵌套调用 pnpm 会报"版本不符"；
   改用 `--ignore-scripts` + `pnpm rebuild better-sqlite3` + 直接 `pnpm --filter <pkg> build`，
   验收走 `node scripts/webui-verify.mjs`。
10. **Dockerfile 要构建新产物**：`pnpm exec vite build --config vite.dsh.config.mjs`
    （产出 `out/renderer-dsh`，复用现有 `COPY out`）。
