# 上游升级流程（保持"一条线更新"）

## 一条命令的判断标准

升级后跑 `pnpm check:upstream-diff`，**通过**意味着：对上游源码只有新增文件与 `patches/` 里那几个受控补丁，
`git rebase upstream/main` 预期零冲突。这是"后续更新也能一条线直接更新"这句承诺的唯一凭据。

## 标准步骤

> 前置：工作树必须干净（`git status` 无未提交改动）。**发布之后**（本仓库有了自己的提交，
> 见 `docs/webui/GitHub-发布方案.md`）走 rebase 版本；发布之前（零自有提交）才可用 fast-forward。

```bash
# 1. 撤销我们的补丁（不撤的话 rebase 会在这几行上冲突）
node scripts/apply-patches.mjs --revert

# 2. 拉取上游
git fetch upstream --tags

# 3. 把我们的提交挪到上游最新之上
git rebase upstream/main
#    发布前（零自有提交）这一句等价于 git merge --ff-only upstream/main；
#    有自有提交后 --ff-only 必然报 "fatal: Not possible to fast-forward"。

# 4. 重打补丁
node scripts/apply-patches.mjs

# 5. 重建 workspace 包（上游若改了 packages/，类型会指向旧 dist）
pnpm build:workspace-runtime

# 6. 重建渲染产物 ← 最容易漏的一步，见下
pnpm exec electron-vite build

# 7. 全量验收
pnpm webui:verify
```

### 发布前后 `package.json` 的处理不同

- **发布前**（`package.json` 是我们的未提交改动）：先 `git stash push -- package.json`，
  rebase 后再 `git stash pop`。
- **发布后**（`package.json` 已随提交入库）：不需要 stash。上游改 `version` 字段**不会**冲突；
  上游同时也在 `scripts` 末尾追加时**会**冲突，**保留双方即可**（良性冲突）。

## ⚠️ 最容易踩的坑：忘记重建渲染产物

`pnpm webui:verify` 里的浏览器类检查，测的是 **`out/renderer/` 里的构建产物**，不是 `src/`。
升级上游后若不跑 `pnpm exec electron-vite build`，测的就是**上一个版本的前端**——
结论会完全错误。这个坑真实发生过一次：

> 升级到 v0.1.1 后没重建，于是"上游对代码块的修复看起来没生效"，
> 白白排查了很久，实际是浏览器里跑的还是旧 bundle。

现在 `pnpm webui:render` 的第一条断言 **R-0** 专门防这个：
构建产物的 mtime 早于渲染层源码就直接 FAIL，并提示该跑什么命令。

> 注：`docker/Dockerfile` 里每次构建都会重新跑 `electron-vite build`，
> 所以**线上镜像不会踩这个坑**——踩坑的只有本地验证。

## v0.1.0 → v0.1.1 实录（2026-09-13）

上游更新内容（53 个文件、+4327 行）与本项目的关系：

| 上游改动 | 对我们的影响 | 处置 |
| --- | --- | --- |
| 修复状态标签/代码块显示（新增 `normalizeMarkdownForRendering.js`） | 正是我们要修的那个问题 | **删掉我们自己的 `patches/0003`**，改用上游实现（它的做法更彻底：未知包裹标签整行移除） |
| 新增轨迹查看（`query.agent.trajectory` + `TrajectoryDialog.jsx`） | 走标准网关注册 | 无需改动，多租户下自动可用（一租户一网关） |
| 新增对话动态设定（4 条 setting_library 路由） | 同上 | 无需改动 |
| `tokens.css`：侧栏宽度 280→328 | 我们的自有页面靠运行时提取令牌 | **零改动**——这正是"运行时提取"相对"抄一份常量"的价值 |
| `titlebar.css` 改侧栏宽度 | 我们的外壳钩子挂在 `.client-titlebar .window-controls` | 钩子未变，`pnpm webui:chrome` 继续通过 |
| `package.json` 版本号 0.1.0→0.1.1 | 我们只加 `scripts`，改的是不同行 | 无冲突（当初坚持只加 script、不改上游文件结构的回报） |
| 补丁目标 `LocalMediaStore.ts`、`RichMessageFrame.jsx` | 上游**未改动**这两个文件 | 两个补丁原样重打，`apply-patches` 零失败 |

结论：`git merge --ff-only` **零冲突**，两个补丁干净重打，门禁通过。

## 检查清单（升级后逐项确认）

- [ ] `node scripts/apply-patches.mjs` 无失败（打不上会立刻报错，这是告警点）
- [ ] `pnpm check:upstream-diff` 通过
- [ ] `pnpm build:workspace-runtime` 已执行（上游改 `packages/` 时必需）
- [ ] `pnpm exec electron-vite build` 已执行（否则浏览器类检查全不可信）
- [ ] `pnpm webui:verify` 全绿（含 R-0 的产物新鲜度断言）
- [ ] 若上游动了 `.client-titlebar .window-controls`，`webui:chrome` 会报警
- [ ] 若上游动了 `tokens.css` 的令牌名，`webui:appearance` 会报警（A-1：提取不到就落兜底）
- [ ] **新克隆的仓库**：先 `git remote add upstream https://github.com/eleckoi/ElecKoi.git`，
     否则门禁找不到 `upstream/main` 会退化成 `v0.1.0` tag 基线，把所有上游改动误报成"我们改了上游"
     （实测会输出 46 个虚假错误）。也可显式传基线：`node scripts/check-upstream-diff.mjs v0.1.1`

## ⚠️ 门禁的盲区：它只看工作树

`scripts/check-upstream-diff.mjs` 用 `git diff --name-status <baseline>` 比对的是
**工作树 vs 上游基线**，因此：

**带着已施加的补丁直接提交，门禁照样判通过**——但提交内容里已经写进了被修改的上游文件，
上游一旦改同一处，rebase 必然冲突（已实测复现）。

所以提交前必须撤销补丁，并加一道人工断言：

```bash
node scripts/apply-patches.mjs --revert
git diff --name-only upstream/main       # 只允许 package.json（及已决定修改的 README.md）
# …提交…
git diff --name-only upstream/main HEAD -- src/main src/renderer   # 必须为空
node scripts/apply-patches.mjs           # 提交后再施加回来（构建需要）
```

注意 `src/main`、`src/renderer` 这两条路径的断言和门禁白名单**必须同步演进**：
一旦决定修改 `README.md`（见 `docs/webui/GitHub-发布方案.md` 决策 4），
就要把 `README.md` 加进 `ALLOWED_MODIFICATIONS`，否则门禁会直接判"修改了上游文件"（已实测）。
