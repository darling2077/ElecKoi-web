### WebUI 侧为这次大改做的适配

上游这版把界面**整体搬进了 DSH 客户端插件体系**（桌面端由 Electron 的自定义协议
`dsh-app` 伺服 DSH 官方 Web 前端 + ElecKoi 的 DSH 页面 + 反代到 DSH 插件宿主）。
我们没有复刻那套 IPC，而是在自己的 HTTP 服务里做同样三件事：伺服 DSH 前端并注入宿主给的
引导项、伺服 `out/renderer-dsh`（上游新增的构建产物）、其余请求反代到该租户的插件宿主。
细节与踩坑记录见 [`docs/webui/上游升级流程.md`](上游升级流程.md) 的「v0.1.10 → v0.2.0 实录」。

要点（都在我们自己的代码里，上游文件零改动）：

1. **桥脚本必须注入 DSH 文档**：ElecKoi 的 DSH 插件在激活阶段就用 `window.eleckoi`，
   拿不到桥会整块界面起不来（表现为「Failed to load plugin」）。
2. **WebSocket 反代**：客户端传输走 `ws://<本站源>/api/remote.mux`，服务端要透传 upgrade。
3. **反代必须真流式**：`/plugins/events` 是 SSE，缓冲会让界面一直"连接中"。
4. **`dsh-app://app` 前缀改写**：插件按需加载的页面写死了这个 Electron scheme，浏览器解析不了。
5. **CSP 用 nonce + 放行 `'unsafe-eval'`**：宿主的引导项是内联脚本，DSH 模块系统还要用 `eval`
   装配插件包；脚本来源仍限 `'self'` + 每次响应的一次性 nonce。
6. **agent 模块被拆成两个插件**：`agentPlugin` 注入的 `fileDrafts` 由 `agentFileDraftsPlugin`
   提供，挂载顺序不能反——少挂一个，**18 条 `command.agent.*` / `query.agent.*` 路由会静默消失**。
7. **新增 `fileOpener` 平台服务**：桌面端是"在文件管理器中显示"，Web 端给诚实的等价物
   （明确提示去下载页取文件）。
8. **ESM 产物补 `require`**：上游 `DshAgentRuntime` 里有一句 CJS 的 `require.resolve('pnpm')`。

另外：跨源卡片帧补丁按上游重构后的组件重新生成；Dockerfile 增加了 DSH 渲染层构建；
构建与验收脚本绕开了"上游把 pnpm 装成依赖导致的版本自检冲突"。

### 一处编排要求（本仓库的 compose 已配好）

容器里的 `/tmp` 是 `tmpfs` 且默认 **noexec**，而 DSH 宿主的原生加载器默认把 `.node` 复制到
`/tmp` 再加载，会直接失败（界面报「界面宿主尚未就绪 … No usable native binding found」）。
`docker/compose.yml` 里已把缓存指到数据卷：`NARB_NATIVE_CACHE_DIR: /data/.native-cache`。
**自建编排请照抄这一条**（`/data` 必须可写且可执行）。

## 这是什么

[ElecKoi](https://github.com/eleckoi/ElecKoi) 的 **Docker 多用户 WebUI 分支**。

上游是 Windows 桌面客户端（Electron）。本分支让同一套内核以 **Docker 服务**运行：
浏览器打开就能用，一个实例服务多个用户，手机竖屏做了适配。

**上游源码零改动。** 我们的东西全部是「新增文件 + 2 个构建期补丁」，
由 `scripts/check-upstream-diff.mjs` 强制保证，因此上游更新时可以一条线 rebase。

## 怎么用

**方式一：拉现成镜像（最快）**

```bash
docker pull ghcr.io/darling2077/eleckoi-web:0.1.10

cp docker/.env.example docker/.env
openssl rand -base64 32        # 生成主密钥，填进 ELECKOI_MASTER_KEY
$EDITOR docker/.env
# 在 .env 里设 ELECKOI_IMAGE=ghcr.io/darling2077/eleckoi-web:0.1.10
docker compose -f docker/compose.yml up -d
```

**方式二：从源码构建**

```bash
git clone -b webui https://github.com/darling2077/ElecKoi-web.git
cd ElecKoi-web
cp docker/.env.example docker/.env
openssl rand -base64 32        # 生成主密钥，填进 ELECKOI_MASTER_KEY
$EDITOR docker/.env
docker compose -f docker/compose.yml up -d --build
```

**首次构建约 20–40 分钟**（apt 依赖 + 886 个 pnpm 包 + Electron 相关下载），
这不是卡住，请勿中断。用方式一可完全跳过。

完成后打开 `http://127.0.0.1:8790/login`，**注册的第一个账号自动成为管理员**。

## 卡片图片：四种做法，改一个变量选

角色卡常把立绘写成外部图床地址，而卡片帧的 CSP 默认拦掉一切外链——
现象是**图片位置一块黑**。下面四种做法各有取舍，改 `ELECKOI_CARD_IMAGE_MODE`
一个变量即可切换，四种都**不需要动上游代码**，也不需要额外跑脚本。

| `ELECKOI_CARD_IMAGE_MODE` | 做什么 | 你这边能看 | 导出给别人 | 数据去哪 | 要配什么 |
| --- | --- | --- | --- | --- | --- |
| `self-hosted`（默认） | 导入时把图传进你自己的图床 | ✅ | ✅ 别人也能取到 | 进你自己的服务器日志 | 图床三件套 + 白名单填图床域 |
| `local` | 导入时存到本地目录，由本服务在卡片源提供 | ✅ | ❌ 别人打不开 | 不出你的机器 | **什么都不用配** |
| `inline` | 导入时内联成 `data:` URI | ✅ | ✅ 图随卡自带 | 不出你的机器 | **什么都不用配** |
| `third-party` | **放行任意 https 图床**、不搬运 | ✅ | ✅（对方不删图就行） | 随图片请求发给**任意域** | 不用配（可选黑名单） |
| `off` | 什么都不做 | ❌ 黑块 | — | 不出去 | — |

怎么选：

- **要发卡给别人** → `self-hosted`（推荐；compose 里已带一个可选的 Zipline 图床：
  `docker compose -f docker/compose.yml --profile images up -d`）。
- **只自己用、想最省事** → `local`：与卡片帧同源，**不需要任何白名单**，零配置。
- **只缺几个小图标** → `inline`：图直接写进卡片数据、随卡走，但别放大图
  （base64 会让卡片数据膨胀，默认只内联 256 KB 以下的）。
- **不想为每张卡加白名单** → `third-party`：直接放行**任意 https 图床**，零配置。
  ⚠️ 代价要讲明白：放开 `img-src` 就等于承认卡片能把你的数据发出去——卡片是作者写的 JS，
  它拼一个 `https://任意域/<聊天内容>.png` 就是一次图片请求（GET），`connect-src 'none'`
  挡不住 `<img>`，数据会落进那个域的访问日志。**选这一档，安全性取决于你导入的卡是否可信。**
  想排除个别域可以用 `ELECKOI_CARD_IMAGE_BLOCKED_HOSTS`，但要说清楚它是**尽力而为**的
  过滤、不是安全边界（CSP 只能"允许哪些源"，做不到"允许全部、排除某几个"）。

## 导入卡片时自动搬图，进度条走完才算导入成功

配好上面的做法后，在浏览器里点「导入」：卡入库 → 界面右下角出现进度条
（`正在把卡片图片搬到你的图床… 12/341`）→ 图片下载、上传、卡里的引用改写完 →
提示「卡片图片已搬好，共 N 张」→ **这时导入才算成功**。

- **同步执行**（`ELECKOI_IMAGE_LOCALIZE_MODE=inline`）：卡一出现在列表里就是最终态，
  不存在"图还在换、人已经进去聊天"的中间态。改成 `background` 则导入立刻返回、后台搬。
- **4 路并发**（`ELECKOI_IMAGE_CONCURRENCY`）：串行搬几百张要几分钟，并发是同步可用的前提。
- 只搬图片（按魔数判定，不认扩展名）；非图片后缀与卡作者写死的 `localhost` 直接跳过；
  网络类失败重试一次、404 之类确定性失败不重试；改写在一个事务里完成。
- 可调上限：单次张数 / 单图字节 / 总时间预算 / 内联上限，见 `.env.example`。

## 部署前必须知道的几条

- `ELECKOI_MASTER_KEY` **一旦设定永不更换**。它是唯一能解开用户已存 API Key 的东西，
  换掉后那些 Key 全部无法解密且不可恢复。
- **公网部署必须同时配** `ELECKOI_CARD_ORIGIN` 与 `ELECKOI_APP_ORIGINS`，
  且两者必须是**不同的源**。只配前者服务会启动失败。
- 反向代理后必须开 `ELECKOI_TRUST_PROXY=1`，否则所有用户共用一个代理 IP，
  累计十次登录失败会让**全站**被限流十五分钟。
  **后端读超时建议 ≥600 秒**：`POST /api/rpc` 会同步等待整个 Agent 回合与导入时的搬图。
- `POST /api/rpc` 的请求体上限是 `ELECKOI_MAX_BODY_BYTES`（默认 128 MB）。导入角色卡会把
  **整张卡的 base64** 放进一次请求，顶到上限会返回明确的 413 并提示怎么处理。

完整说明见仓库 [`docs/webui/`](https://github.com/darling2077/ElecKoi-web/tree/webui/docs/webui)，
交给 AI 助手部署可让它直接读根目录的 [`CLAUDE.md`](https://github.com/darling2077/ElecKoi-web/blob/webui/CLAUDE.md)。

### 卡片图片这条线（本版重点）

- **四种做法一个开关**：`ELECKOI_CARD_IMAGE_MODE` = `self-hosted` / `local` / `inline` /
  `third-party` / `off`，compose 与 `.env.example` 里逐项写清了每种要配什么、代价是什么。
  `third-party` 是"放行任意 https 图床"，不用再为每张卡补白名单；另给一个可选的
  主机名黑名单（`ELECKOI_CARD_IMAGE_BLOCKED_HOSTS`），并在验收里用真实浏览器验证了
  "被屏蔽的域一次请求都收不到"。
  四种做法都在验收里跑过真实的导入与取回（`self-hosted` 与 `local` 的图可直接按新地址取回，
  `inline` 产出 `data:` URI）。
- **导入即搬图 + 进度条**（见上）。
- **可选自带图床（Zipline）**：`--profile images` 一条命令启用，别人能凭邀请码注册、上传、
  翻自己的图、复制链接。**不启用完全不影响默认部署**（默认 `up -d` 只起 `eleckoi-web`）。
  配置全部在 `docker/.env` 的 `ZIPLINE_*` 段，由 compose 逐项传入——
  第三方镜像拿不到 `ELECKOI_MASTER_KEY`。
- **多租户下同一张图只存一份**：按内容（sha256）查跨租户共享的索引，朋友导入你已经导过的同一张卡时，
  直接复用图床上已有的地址、**不再重复上传**（复用前会探活，图被删了就重传）。
  实测：两个用户各导入同一张 12 图的卡，图床只收到 12 次上传（不去重是 24 次），
  且两张卡指向完全相同的那组图。卡里重复出现的同一张图也只传一次。
- **离线批量搬迁脚本** `docker/rewrite-card-images.mjs`：用于已有数据的一次性搬迁
  （换图床、补搬历史卡），幂等、默认 dry-run、改前自动备份。
- **批量导入工具** `pnpm webui:import-cards`：一次导入整个目录的卡，
  走应用自己的导入通道，默认只预检不写库。

### 修复

- **上传大图 / 批量导入报「与桌面服务的连接已断开」**：根因是 `POST /api/rpc` 的请求体
  上限被硬编码成 8 MB，超限直接掐断连接，浏览器只能报那句毫无信息量的话。
  现在上限可配（默认 128 MB），超限返回**明确的 413**（含当前上限与下一步），
  且超限之后连接仍然可用；读请求体也改成边收边解码，省一份内存拷贝。
- **卡片图片显示为黑块**：由上面的四种做法解决；文档里给了排查顺序
  （先看是不是跨源引用 → 再看 CSP → 最后才怀疑卡片本身）。
