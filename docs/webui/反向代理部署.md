# 公网部署：反向代理（lucky）+ 固定端口 + 子域分流

示例拓扑（把域名、证书与内网 IP 换成你自己的即可）：

```
浏览器
  │  https://app.example.com:57789       ← 泛域名证书 *.example.com + 泛解析
  │  https://cards.example.com:57789
  ▼
内网穿透隧道（frp 等）或 IPv6 直连
  ▼
lucky（host 网络，固定监听 57789，按 SNI/Host 分流）
  ├── app.example.com    → http://192.0.2.10:8790   应用
  └── cards.example.com  → http://192.0.2.10:8791   卡片源
  ▼
容器 eleckoi-web（容器内只监听 8790）
```

端口固定 57789、按子域分流，所以**加卡片源只需要在 lucky 里多一条子域规则**：
证书是 `*.example.com`（泛域名）、DNS 是泛解析，都不用动；frp 也不用动（它只转发裸 TCP）。

## 为什么卡片必须是另一个子域

卡片是作者写的 HTML/JS，跑在 iframe 里。如果和应用同源，卡片脚本就能直接读
`parent.eleckoi`，等于拿到用户的会话能力。所以卡片帧必须来自**另一个源**——
`https://cards.example.com:57789` 与 `https://app.example.com:57789` 主机不同，
是天然的两个源，隔离成立。

⚠️ 不能用「同域不同路径」代替：那样仍是同一个源，隔离等于没有。

## lucky 需要配的两条规则

| 域名 | 监听端口 | 后端 | 状态 |
| --- | --- | --- | --- |
| `app.example.com` | 57789 | `http://192.0.2.10:8790` | 已配 |
| `cards.example.com` | 57789 | `http://192.0.2.10:8791` | 已配置 |

两条规则用同一张 `*.example.com` 证书。

### 代理必须传递的头

应用侧已经对代理做了适配（`ELECKOI_TRUST_PROXY=1`），但代理得把信息给出来：

| 头 | 为什么需要 | 不给会怎样 |
| --- | --- | --- |
| `Host`（保留原值）**或** `X-Forwarded-Host` | 卡片源按对外 Host 分流；写操作的同源校验也要用 | 卡片源失配（卡片打不开）；若两者都没有，登录会被判成跨站 403 |
| `X-Forwarded-Proto: https` | 让会话 Cookie 自动带上 `Secure` | 功能正常，但 Cookie 少一个安全属性 |
| `X-Forwarded-For`（**覆盖**而非追加） | 限流按真实客户端 IP 计 | 所有公网用户共用一个 IP，累计十次失败就全站 429 十五分钟 |

> nginx 默认会把 `Host` 换成上游地址（`$proxy_host`），必须显式
> `proxy_set_header Host $host;`。lucky 实测会保留原始 Host，所以现状可用；
> 即使将来被改写，`X-Forwarded-Host` 也能兜住。

### SSE（`/api/events`）相关

应用的实时更新走 SSE。服务端已经带 `X-Accel-Buffering: no` 并且每 15 秒发一次心跳注释，
正常情况下不用配。若界面不自动刷新：

- 关掉响应缓冲（nginx 的 `proxy_buffering off`，lucky 里的响应缓冲/压缩类选项）；
- 把后端读取超时放到 ≥ 60 秒（心跳是 15 秒一次）；
- 不要在代理上把 `text/event-stream` 做 gzip。

### ⚠️ 后端超时必须放大，否则长回合会被掐断

`POST /api/rpc` 是**同步等到整个 Agent 回合结束**才返回的
（`server.ts`：`await binding.gateway.dispatch(...)` 完成后才 `sendJson`），
流式增量另走 SSE。也就是说一次长回复期间，这个 POST 会一直挂着不返回。

代理的默认读超时往往只有 60 秒（nginx `proxy_read_timeout` 默认值），
超时即断连——用户看到报错，而服务端其实还在正常生成。

**请把两条规则的后端/读取超时设到 300 秒以上，或直接关掉该超时。**
若代理不支持放大超时，再考虑改成"POST 立即返回 + 结果走 SSE"，
但那要动核心数据路径，非必要不做。

同理，请求体大小上限也别设太小：上传头像、角色卡插图都走这条链路。

## 刻意不设的变量

```
# ELECKOI_SECURE_COOKIES=1   ← 不要设
```

它会给**所有** Cookie 加 `Secure`，而带 `Secure` 的 `Set-Cookie` 在明文连接上会被浏览器
直接丢弃——等于把局域网 `http://192.0.2.10:8790` 的登录打死。
现在改为按请求判定：HTTPS 入口带 `Secure`，明文入口不带（`src/web/http/cookies.ts`）。
两种入口各自持有自己的 Cookie（Cookie 本就按主机隔离），互不影响。

## 验收

`pnpm webui:proxy`（8 条断言，已并入 `pnpm webui:verify`）模拟上述全部情形：

- **P-1/P-2** 代理保留 Host、以及代理改写 Host 只给 `X-Forwarded-Host`，两种都要能登录。
- **P-3** 陌生 `Origin` 仍被拒（白名单不是放行一切）。
- **P-4** HTTPS 入口的 Cookie 带 `Secure`，明文入口不带。
- **P-5** 限流按 `X-Forwarded-For` 隔离：一个 IP 打满不影响别人。
- **P-6** 卡片帧只在卡片域提供，应用域上取不到（跨源隔离成立）。
- **P-7/P-8** 卡片帧的 `frame-ancestors` 只放行应用源，应用文档的 `frame-src` 放行卡片源。

公网实测（示例域名为占位符，实测时用真实域名）：

```bash
curl -s -o /dev/null -w "%{http_code}\n" https://cards.example.com:57789/__eleckoi/card-frame.html
# → 200，且响应头带 frame-ancestors https://app.example.com:57789 http://192.0.2.10:8790

# 经公网入口的会话 Cookie（应带 Secure）
curl -s -D - -o /dev/null -X POST https://app.example.com:57789/api/auth/logout | grep -i set-cookie
# → ... SameSite=Lax; Max-Age=0; Secure

# 局域网明文入口（不应带 Secure，否则浏览器会直接丢弃而登录不上）
curl -s -D - -o /dev/null -X POST http://192.0.2.10:8790/api/auth/logout | grep -i set-cookie
# → ... SameSite=Lax; Max-Age=0
```

公网入口与局域网入口的登录页截图逐字节相同（同一浏览器、同一窗口尺寸），
说明经代理后令牌样式表与 Noto Sans 字体都正常加载。
