## 0. 结论：公网前的那道硬门槛已经跨过

上游用 `srcDoc` 渲染角色卡，srcdoc **继承父文档源**，于是卡片里的 JS 可以直接
`parent.eleckoi.request(...)` 打穿全部 68 条 IPC。本报告的核心就是**真实浏览器里证明了这道口子已被关上**：

| 断言 | 结果 |
|---|---|
| 恶意卡片访问 `parent.eleckoi` | **blocked** |
| 恶意卡片访问 `parent.document` | **blocked** |
| postMessage 通道（卡片正常功能） | **ok** |

验证方式不是模拟：应用源 `http://127.0.0.1:<port>`、卡片源 `http://127.0.0.2:<port>`
（不同源、同一进程服务），用无头 Chromium 加载真实页面并投递一段恶意卡片 HTML。

## 1. 交付内容

### 1.1 方案 A：卡片跨源承载

```
应用源 app.example.com                卡片源 cards.example.com
┌──────────────────────────┐          ┌──────────────────────────┐
│ 上游渲染层（零改动）        │          │ /__eleckoi/card-frame.html│
│  · 会话 Cookie、全部 IPC  │          │  （我们自己的引导页）      │
│  ┌────────────────────┐  │ postMsg  │  · 只接受应用源投递的文档  │
│  │ RichMessageFrame   │──┼─────────▶│  · document.write 写入    │
│  │ src=卡片源帧页面    │  │  文档     │                          │
│  └────────────────────┘  │          │ 卡片代码运行在此源内       │
│         ▲                │          │ → parent.eleckoi 跨源不可达│
│         └── height / author-request ─┤                          │
└──────────────────────────┘          └──────────────────────────┘
```

关键点：`document.open()` + `write()` 会替换文档内容但**保留本源的 URL 与源**，
因此卡片照常拥有自己的 DOM 与 localStorage，只是够不到应用源。

### 1.2 渲染层补丁（唯一必须改上游源码的地方）

`patches/0002-cross-origin-card-frame.patch`（+24/−1），改
`src/renderer/src/modules/authorFrontend/components/RichMessageFrame.jsx`：

- 读取服务端注入的 `window.__ELECKOI_WEB__.cardOrigin`；
- 配置了卡片源时用 `src=` 指向卡片帧页面，否则**保持原 `srcDoc` 行为**（平滑降级）；
- 增加一次 `eleckoi:card-ready` → `eleckoi:card-document` 的握手。

既有的高度/author 协议**完全复用**：它们本就检查 `event.source` 与 `channel`，跨源后语义不变。

git 树里上游文件保持原样，补丁由 `scripts/apply-patches.mjs` 在构建期施加；
可更新性门禁会校验改动量与补丁逐行一致。

### 1.3 卡片源的最小攻击面

卡片源只提供两个路由，其余一律 404：

| 路由 | 说明 |
|---|---|
| `/__eleckoi/card-frame.html` | 引导页，带卡片 CSP |
| `/media/v1/*` | **仅**接受带有效签名的请求 |

`/`、`/api/*` 在卡片源上一律 404——已实测确认。卡片源不解析会话、不挂载租户。

### 1.4 卡片 CSP

```
default-src 'none'; script-src 'unsafe-inline' 'unsafe-eval'; style-src 'unsafe-inline';
img-src 'self' data: blob:; media-src 'self' data: blob:; font-src 'self' data:;
connect-src 'none'; frame-src 'none'; object-src 'none'; base-uri 'none'; form-action 'none'
```

取舍：卡片本来就要跑内联脚本与样式，所以 script/style 必须放开 inline；
但把**网络出口收紧**——`connect-src 'none'` 挡住 fetch/XHR 外传数据，
`frame-src 'none'` 挡住嵌套 frame。卡片的媒体都来自卡片源自身（见下），`'self'` 足够。

### 1.5 签名媒体 URL

跨源卡片帧不携带应用源的会话 Cookie，因此媒体必须靠 URL 签名：

- 载荷 `media|<tenantId>|<资源路径>|<过期时间>`，HMAC-SHA256，密钥由主密钥 HKDF 派生；
- 网关出站时把 `/media/v1/...` 就地替换为带 `t/exp/sig` 的 URL（有效期 6 小时）；
- 服务端与卡片源都先验签名，验过即放行，无需 Cookie。

实测：无 Cookie 带签名 → `200 image/png`；篡改签名 → 回落会话门禁；无签名无 Cookie → 不放行。

### 1.6 启动期安全校验

配置了 `ELECKOI_CARD_ORIGIN` 却没配 `ELECKOI_APP_ORIGINS` 时**服务直接启动失败**——
否则卡片帧会拒绝一切文档投递，表现为"卡片永远空白"这种难查的静默故障。
（这个坑是本轮实际踩到的：最初白名单为空，卡片帧静默丢弃了文档。）

## 2. 验证方式上的一个坑（值得记录）

测试页最初放在应用源上，结果浏览器被 302 带到登录页——**测试页本身也被鉴权门禁拦住**。

最终改为用**单租户无鉴权模式**跑这个验收：跨源隔离与登录门禁互不相干，
去掉门禁既能让测试页直接加载，也避免为测试在生产代码里开后门。

另一个坑：卡片帧会 `document.write` 替换文档，页面永远到不了"load 完成 + 网络空闲"，
`--dump-dom` 会挂死。改为让页面把结果 `sendBeacon` 回测试进程，收到即杀浏览器，不依赖快照时机。

## 4. 本轮追加（公网部署所需）

### 4.1 应用源 CSP 与安全响应头

应用文档现在带完整 CSP，由 `src/web/http/securityHeaders.ts` 生成：

```
default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline';
img-src 'self' data: blob:; media-src 'self' data: blob:; font-src 'self' data:;
connect-src 'self'; frame-src 'self' <卡片源>; worker-src 'self' blob:;
object-src 'none'; base-uri 'none'; form-action 'none'; frame-ancestors 'none'
```

`script-src` 能收到 `'self'`（不开 `'unsafe-inline'`），是因为**注入的卡片源配置随桥脚本
一起下发**，而不是单独一个内联 `<script>`。登录页另有自己的 CSP（它本来就带内联样式与脚本）。

同时下发：`x-content-type-options: nosniff`、`x-frame-options: DENY`、
`referrer-policy`、`permissions-policy`、`cross-origin-opener-policy`。
另有排障开关 `ELECKOI_DISABLE_CSP=1`（只去 CSP，保留其余头），用于做对照实验。

**验证**（`pnpm webui:csp`，6/6）：不只是断言响应头，而是用真实浏览器渲染一遍，
确认界面照常出现（DOM 26 689 字节，含应用文案）——加 CSP 最大的风险是静默把应用打坏。

> 过程中一个值得记的连锁反应：CSP 上线后，**卡片隔离测试自己的回传也失效了**——
> 测试页的内联脚本被 `script-src 'self'` 拦掉，改用外链脚本后
> `navigator.sendBeacon` 又被 `connect-src 'self'` 拦掉，最终改成页面跳转回传。
> 这反过来证明 CSP 确实在生效。

### 4.2 反向代理样例（`docker/Caddyfile`）

两个域名分别转给同一容器（服务端按 Host 区分），Caddy 自动申请 TLS：

- 应用域：`flush_interval -1` 关闭缓冲，否则 SSE 事件会被代理攒着不发；
  登录接口加 IP 限流；HSTS。
- 卡片域：只承载卡片帧与签名媒体，容器端其余路径一律 404。

### 4.3 AGPL §13 源码入口

新增 `ELECKOI_SOURCE_URL`：配置后在登录页渲染「查看对应源代码」链接。
未配置时服务启动打印警告。链接只接受 http(s)，避免配置项变成注入点。

### 4.4 并发回合配额

一个 Agent 回合会拉起一个独立 node 子进程，**没有上限时单个用户开多个会话就能拖垮整台机器**。

- 在 `command.agent.start` / `command.agent.regenerate` **进入处理器之前**占位，超限直接拒绝；
- 回合以 `agent.run.finished` / `agent.run.failed` 结束（或请求未被接受）时释放；
- 兜底：超过 `runTimeoutMs`（默认 30 分钟）的名额强制回收，避免事件丢失把用户永久锁死。

实测（`pnpm webui:quota`，7/7）：占用后第二个并发回合被拒；结束释放；释放后可再次开始。

> 实现时踩到一个别名 bug：清理函数在槽位为空时 `delete` 了 map 条目，却把新数组返回给
> `begin`，于是 `begin` push 进了一个游离数组——配额形同虚设。现已把结果写回 map。

### 4.4b 局域网 / 公网访问

compose 默认只把端口绑在**回环地址**（`127.0.0.1`），这是刻意的：默认暴露面为零。
要给别的机器访问，必须显式指定绑定的网卡：

```bash
export ELECKOI_BIND=192.0.2.10          # 或 0.0.0.0（暴露面更大）
export ELECKOI_PORT_HOST=8790              # 应用域
export ELECKOI_CARD_PORT_HOST=8791         # 卡片域（必须与卡片域配置一致）
export ELECKOI_CARD_ORIGIN=http://192.0.2.10:8791
export ELECKOI_APP_ORIGINS=http://192.0.2.10:8790
```

注意三点：

1. **卡片域与应用域必须是不同源**。同一 IP 的不同端口就满足（浏览器按 协议+主机+端口 判定源）。
   两个端口都映射到容器的 8790，由服务端按 Host 区分：卡片域只暴露卡片帧与签名媒体。
2. `ELECKOI_CARD_ORIGIN` / `ELECKOI_APP_ORIGINS` 必须写**浏览器实际访问的地址**。
   卡片源写错时表现为「卡片永远空白」——卡片帧会静默拒绝文档投递。
3. 服务本身没有鉴权门禁之外的访问控制，**开放注册默认是开的**。
   让局域网用户建完账号后建议设 `ELECKOI_ALLOW_REGISTRATION=0`。

### 4.5 备份与恢复（`docker/backup-tenants.mjs`）

上游没有迁移链也没有账号级导出，**备份是自建服务唯一的数据保险**。

- SQLite 一律用 `VACUUM INTO` 取一致性快照（直接拷贝可能丢 WAL 里未合并的数据）；
- 归档含 `manifest.json`（格式、时间、租户清单）+ 控制面库 + 各租户目录；
- `verify` 解包后校验结构与每个租户库的 `integrity_check`；
- `restore` 拒绝写入非空目录，避免覆盖线上数据。

实测（`pnpm webui:backup`，7/7）：两个用户写数据 → 备份 → 校验 → 恢复到新目录，
**恢复后用户、租户、各租户的业务设置都还在**；恢复到非空目录被拒绝。
