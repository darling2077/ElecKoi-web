# 卡片外链图片本地化

## 现象：卡片里的图全黑

角色卡把立绘直接写成外部图床地址（`<img src="https://i.postimg.cc/xxx.png">`）时，
Web 端看到的是一块**纯黑**，而桌面端同一张卡显示正常。

两个因素叠加：

1. **卡片帧的 CSP 默认是 `img-src 'self' data: blob:`**（`src/web/http/cardFrame.ts`）。
   卡片来自 `ELECKOI_CARD_ORIGIN`，图床是第三个域，浏览器直接拦掉请求
   ——不是加载失败，是**请求根本没发出去**（已在真实浏览器里验证：白名单外
   的图，图床服务器收不到任何请求）。
2. 卡片的 CSS 常把图片容器的底色写成 `--bg: #1a1a1a` 配黑色渐变遮罩，
   加载不出来就呈现为一块黑，看起来像"卡片坏了"。

桌面端不受影响：它用 `srcDoc` 渲染，没有这层 CSP。

> 排查口诀：**图能单独打开 ≠ 卡片能显示**。先看卡片是不是跨源引用，
> 再看 CSP，最后才怀疑卡片本身。

## 两条路，先选一条

| | 放行图床 | 本地化改写（推荐配合前者） |
| --- | --- | --- |
| 做法 | `ELECKOI_CARD_IMAGE_ORIGINS` 填图床源 | 把图搬到自己的图床并改写卡里的引用 |
| 好处 | 一分钟生效，不动数据 | 卡片导出给别人也不失效；原图床删图不影响 |
| 代价 | 原图床删图，卡片就空了 | 需要跑一次工具、占自己的磁盘 |

两者**不冲突**：本地化改写完成后，仍需把**自己的**图床域配进白名单，
因为改写后的引用换成了你自己的域，同样属于跨源。

### ⚠️ 只放行你自己的图床

宽松到"能加载图片"，就等于承认卡片可以**通过图片 URL 把数据发出去**：
卡片是作者写的 HTML/JS，它拼一个 `https://图床/<聊天内容>.png` 就能外传。

- 放行**自己的**图床：数据落在你自己服务器的访问日志里，作者读不到 → 可接受。
- 放行**第三方公共**图床（postimg.cc、catbox 之类）：那类站点任何人可读，
  等于把聊天内容公开出去 → **不要这么做**。

正因如此，`ELECKOI_CARD_IMAGE_ORIGINS` 只接受纯源、且不支持通配符。

## 一、放行图床

```bash
# docker/.env
ELECKOI_CARD_IMAGE_ORIGINS=https://img.example.com
```

规则与报错都在 `.env.example` 里写明了，要点：

- 只接受 `scheme://host[:port]`；带路径、查询串、通配符都会被拒绝并**启动失败**。
- 逗号分隔可以填多个（例如同时放行图床和一个局域网相册站）。
- 服务启动时会打印生效的清单，改完记得重启容器。

## 二、把自己的图床跑起来（Zipline）

图床不是"一个能放文件的目录"就够了——别人用你的图床时，需要能注册、能上传、
能翻自己的图、能复制链接。所以这里直接带一个 [Zipline](https://zipline.diced.sh)：

```bash
# 生成两个密钥，填进 docker/.env 的「自带图床」段（.env.example 里有逐项说明）
openssl rand -base64 24 | tr -dc A-Za-z0-9 | cut -c -24    # → ZIPLINE_DB_PASSWORD
openssl rand -base64 42 | tr -dc A-Za-z0-9 | cut -c -32    # → ZIPLINE_CORE_SECRET
$EDITOR docker/.env

docker compose -f docker/compose.yml --profile images up -d zipline-db zipline
```

配置全部走 compose 的 `environment` 逐项传入，**没有第二个 env 文件**：
好处是只有这几个变量会进图床容器，`ELECKOI_MASTER_KEY` 之类的凭据不会被第三方镜像读到。

它在 `images` profile 下，**不显式启用就不会启动**：平时那条
`docker compose -f docker/compose.yml up -d` 完全不受影响（已验证：默认路径解析出的
服务只有 `eleckoi-web`）。图床同时包含一个 Postgres 容器（Zipline 只支持 Postgres），
两个都限了内存。

### 配好之后要做的三件事

1. **Lucky 加一条子域分流**：`img.kidamita.top` → `http://192.168.5.254:8792`
   （与 `ai.` / `cards.` 同样的做法）。Zipline 需要的代理头已由
   `CORE_TRUST_PROXY=true` + `CORE_RETURN_HTTPS_URLS=true` 处理。
2. **打开 `https://img.kidamita.top:57789`**，首次进入是安装向导，创建超级管理员账号。
3. **确认注册是邀请码制**：示例配置是 `FEATURES_USER_REGISTRATION=false` +
   `INVITES_ENABLED=true`，也就是"没邀请码注册不了、有邀请码就能注册"。
   邀请码在后台「邀请码」页生成后发给人。**这两个开关很容易配反**
   （`FEATURES_USER_REGISTRATION=true` 会让任何人直接注册，邀请码形同虚设），
   原因写在 `docker/.env.example` 的「自带图床」段里。
   **别忘了给每个账号设配额**——单人配额没有环境变量，只能在后台「用户」页逐个设，
   否则公网放开后会被刷满磁盘。

### 让脚本能传图：生成 API 令牌

后台「账号设置」里生成一个 API 令牌（`ZIPLINE_CORE_SECRET` 参与加密，所以**换掉它
会让已发的令牌全部失效**）。令牌就是后面 `--upload-token` 的值。

## 三、批量本地化改写

工具：`docker/rewrite-card-images.mjs`。它扫描角色卡散落图片引用的所有位置
（正文内容、正则替换、设定项、变量配置、聊天背景），逐个下载、用**魔数**判定
是不是图片，是图片就搬到你的图床，然后把卡里的引用改成图床地址。

两种搬运方式，按图床选一种：

```bash
# A) 传进图床服务（推荐，Zipline）
node docker/rewrite-card-images.mjs /vol2/docker/volumes/docker_eleckoi-data/_data/tenants \
  --public-base https://img.kidamita.top:57789 \
  --upload-api https://img.kidamita.top:57789 \
  --upload-token <API 令牌> \
  --apply

# B) 落到本地目录（交给你自己的静态服务）
node docker/rewrite-card-images.mjs /vol2/docker/volumes/docker_eleckoi-data/_data/tenants \
  --public-base https://img.kidamita.top:57789 --upload-dir /srv/images --apply
```

先不加 `--apply` 跑一次是 dry-run（只报告、不下载、不改库）。

参数与行为：

- 第一个参数可以是**单个库文件**、**某个租户目录**，也可以是**整个数据根目录**
  （自动遍历 `tenants/*/db/eleckoi-common.sqlite3`）。
- `--public-base` 是图床**对外**的地址：既用于识别"这张图已经搬过了"，也用于
  重写引用。用 API 方式时**请用公网地址调 API**，理由见下。
- `--upload-folder` 可选，把图都传进某个文件夹（值是该文件夹的 ID）。
- `--max-bytes`（默认 20 MB）、`--timeout-ms`（默认 20 s）。
- **地址以图床返回的为准**：脚本取服务返回的文件路径、再套回 `--public-base`，
  所以从内网 IP 还是公网域名调 API，写进卡里的地址都是对的那个。
- **文件名按内容 sha256 前 32 位命名**：同一张图多处引用只存一份（API 方式下
  同一 URL 在一次运行里也只传一次）；已经是自己域名的引用直接跳过（幂等）。
- 判定为"不是图片"的地址（字体 CSS、XML 命名空间、网页）保留原样，
  本机地址（localhost）直接跳过；网络类失败会自动重试一次并单独列出。
- 写入在一个事务里完成；任一步失败会回滚，并留下改前备份。

### 执行时机：先停容器

SQLite 库在容器运行时处于 WAL 状态，**不要**对着正在写入的库改数据。
稳妥顺序：

```bash
docker compose -f docker/compose.yml stop
node docker/rewrite-card-images.mjs ... --apply
docker compose -f docker/compose.yml start
```

改完别忘了一、里的 `ELECKOI_CARD_IMAGE_ORIGINS`，否则改写后仍然被 CSP 拦。

## 实测记录（2026-09-16）

在一份真实租户库（14 张卡、5 个会话）上跑：扫描到 25 个外部 URL，判定为图片
16 个（含 4 个 CC 协议 SVG 徽标、1 个 2 MB GIF、7 张别人自建图床的头像），
9.1 MB 落盘，改写 3 条记录（含「破碎与重生」状态栏里的 4 张立绘）；
"不是图片"6 个、"直接跳过"3 个（本机地址、字体 CSS 等）。二次运行改写 0 条，
确认幂等。

改前那 4 张立绘在服务端都是 HTTP 200、能单独打开，但卡片里呈现全黑
——正是本文第一节描述的 CSP 拦截。

## 别忘了最后一步

搬完图后，把**图床自己的域**加进白名单，否则改写后的引用照样被 CSP 拦：

```bash
# docker/.env
ELECKOI_CARD_IMAGE_ORIGINS=https://img.kidamita.top:57789
```

然后 `docker compose -f docker/compose.yml up -d` 重建容器（改 `.env` 不会
自动进容器，必须重建），启动日志里会打印生效的清单。
