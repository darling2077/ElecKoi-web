## 3. 媒体链路（`pnpm webui:media`）与一个上游真 bug

| 断言 | 证据 |
|---|---|
| 上游产出引用 | `eleckoi-media://asset/v1/<ownerHash>/avatar/<sha>.png` |
| 出站重写为浏览器可用 URL | `/media/v1/<ownerHash>/avatar/<sha>.png` |
| 正常回源 | `GET` → `200 image/png` 70 B |
| 路径穿越全部被挡 | `../`、`..%2f`、`%2e%2e%2f`、`....//` 四种变形均未返回目标文件内容 |

### 修掉的上游 bug（Linux/macOS 上媒体必然 404）

`src/main/platform/filesystem/LocalMediaStore.ts:97,103` 用硬编码反斜杠拼路径根：

```ts
const root = `${resolve(this.versionRoot())}\\`
return candidate.startsWith(root) ? candidate : undefined
```

`resolve()` 在 POSIX 返回 `/data/.../v1`，而 `root` 变成 `/data/.../v1\`，
`candidate` 永远不以它开头 → **`pathForReference` 恒返回 `undefined`**，
`removeOwner` 则恒抛「本地媒体目录越界」。

全仓核查后确认：这个写法只出现在这 2 行，其余位置都正确使用了 `/[\\/]/`。
影响面是**所有非 Windows 部署**（不只是本移植），值得回报给上游。

修法用跨平台判定（与上游 `DshRuntime.isDescendant` 同款思路）：

```ts
function isInside(root: string, candidate: string): boolean {
  const path = relative(root, candidate)
  return path.length > 0 && !path.startsWith('..') && !isAbsolute(path)
}
```

## 4. 可更新性门禁与补丁机制

### 4.1 `patches/` + `scripts/apply-patches.mjs`

上游源码的必要改动写成补丁，**git 树里的上游文件保持与上游一致**：

- `node scripts/apply-patches.mjs`：幂等施加；**打不上即失败**——上游一旦改到我们依赖的行，
  立刻报警要求人工复核，这正是可更新性需要的闸门。
- 支持 `--check`（只验证）与 `--revert`（撤销）。
- 当前 1 个补丁：`0001-local-media-path-separator.patch`（+13/−5）。
- 所有 `webui:*` 构建脚本都会先跑 `apply-patches`，避免忘记施加而静默构建出坏产物。

### 4.2 `scripts/check-upstream-diff.mjs`（`pnpm check:upstream-diff`）

规则：

1. 上游文件**不得删除**。
2. 上游文件的合法改动只有两类：
   - `package.json` —— 只允许**新增 script**，其余字段与基线逐字比对；
   - `patches/*.patch` 覆盖的文件 —— 当前改动量必须**与补丁完全一致**（不得夹带私货）。
3. 新增文件必须落在白名单（`src/web/`、`docker/`、`patches/`、`docs/webui/`、两个 scripts、`.dockerignore`）。

实测输出：

```
基线：upstream/main（0f55dac）
改动：上游文件修改 2 个、删除 0 个；新增 30 个；补丁 1 个文件
· src/main/platform/filesystem/LocalMediaStore.ts：已施加补丁 0001-…（+13/-5）
· package.json 新增 script：webui:build, webui:poc, webui:serve, webui:agent, webui:typecheck, webui:media, check:upstream-diff

可更新性门禁通过：对上游仅有新增与受控补丁，rebase 预期零冲突。
```

> 基线取 `upstream/main` 而非 tag `v0.1.0`：tag 指向初始提交，会把上游自己的
> 第二个提交误判成我们的改动。脚本按 `upstream/main` → `v0.1.0` 顺序回退。

## 5. Docker

`docker/Dockerfile`（多阶段）+ `docker/compose.yml` + `.dockerignore`。

要点：

- 阶段 1 完整安装并构建；`ELECTRON_SKIP_BINARY_DOWNLOAD=1` 跳过 Electron 二进制（Web 端运行时不需要）。
- `better-sqlite3` 在容器内针对目标平台编译（builder 阶段装 python3/make/g++）。
- 两阶段**保持同一路径 `/app`** 复制，使 pnpm 的 workspace 符号链接继续有效。
- 构建产物：`out/renderer`（`electron-vite build`）+ `out/web/serve.mjs`（vite SSR 构建）。
- 运行阶段：非 root（uid 10001）、`/data` 数据卷、健康检查打 `__eleckoi/web-bridge.js`。
- compose 默认**只绑 127.0.0.1**，并附容器加固（`no-new-privileges`、`cap_drop: ALL`、
  `read_only` 根文件系统、tmpfs、内存与 PID 限制）。
- `ELECKOI_MASTER_KEY` 由 compose 强制注入；缺失时服务只临时生成并**显式告警**重启后密钥不可解密。

> M1 形态**没有鉴权**，只能本地/内网使用；公网暴露等 M2（用户体系）与 M3（加固）。

这是**一次性成本**：该层成功后会被缓存，后续重建不再重复。

   实际路径是 `packages/sdk/author/package.json`；且该写法的 `COPY a b` 是

   已在 builder 阶段安装 git，并让脚本在 git 缺失时给出准确报错。
